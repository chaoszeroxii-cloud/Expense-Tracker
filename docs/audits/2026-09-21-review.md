- ไม่ทดสอบเจาะบริการ production/cloud ไม่ส่งอีเมลหรือเรียก AI ที่คิดเงิน และไม่แก้รายการเงินจริง

### A01 — P1: สวมอีเมลไว้ก่อน แล้วคงสิทธิ์เข้าเมื่อเจ้าของเชื่อมบัญชีจริง

ตำแหน่ง: [auth.service.ts:197](<D:/Web App Project/expense-tracker/backend/src/modules/auth/auth.service.ts:197>) และ [auth.service.ts:208](<D:/Web App Project/expense-tracker/backend/src/modules/auth/auth.service.ts:208>)

เมื่อ Google ส่งอีเมลที่ยืนยันแล้ว ระบบเชื่อมเข้าบัญชีเดิมที่มีอีเมลตรงกันทันที โดยไม่ได้พิสูจน์ว่าคนสร้างบัญชีเดิมเป็นเจ้าของอีเมล และยังคงรหัสผ่าน/ช่องทางโซเชียลเดิมไว้

หลักฐานสองกรณี:

1. สมัครแบบ local ด้วยอีเมลของบุคคลอื่นที่ยังไม่อยู่ในระบบ → เจ้าของอีเมลเข้า Google ครั้งแรก → ได้ user ID เดียวกัน และรหัสผ่านที่ผู้สวมอีเมลตั้งไว้ยัง login ได้
2. โซเชียลที่ไม่ส่งอีเมลยืนยันใช้ `clientEmail` จองอีเมลไว้ → เจ้าของเข้า Google → เจ้าของรีเซ็ตรหัสผ่าน → JWT เก่าถูกปฏิเสธ 401 ตามที่ควรเป็น แต่โซเชียลเดิมยัง login ใหม่เข้าบัญชีเดียวกันได้

ผลกระทบ: ผู้ที่จองอีเมลไว้ก่อนอาจเข้าดูหรือแก้ข้อมูลการเงินที่เจ้าของเพิ่มภายหลังได้ ต้องเกิดการจองก่อนและการเชื่อมบัญชีตามเงื่อนไขข้างต้น ไม่ใช่การยึดบัญชีใดก็ได้เพียงรู้อีเมล

แนวแก้: แยกสถานะ verified email จากอีเมลที่ผู้ใช้กรอกเอง บัญชีที่ยังไม่ยืนยันต้องไม่เป็นปลายทาง auto-link; การเพิ่มช่องทาง login ต้องพิสูจน์การครอบครองบัญชีเดิมและ provider ใหม่ พร้อมมีวิธีจัดการ credentials ที่ผูกไว้อย่างชัดเจน

### A02 — P1: Push subscription เปิดให้เซิร์ฟเวอร์เชื่อมต่อ URL ภายใน

ตำแหน่ง: [notifications.dto.ts:14](<D:/Web App Project/expense-tracker/backend/src/modules/notifications/notifications.dto.ts:14>) และ [notifications.service.ts:223](<D:/Web App Project/expense-tracker/backend/src/modules/notifications/notifications.service.ts:223>)

`endpoint` ตรวจเพียง string/ความยาว แล้วส่งให้ `webpush.sendNotification` โดยตรง ไม่มีการจำกัด push provider, host, port หรือ IP ปลายทาง

หลักฐาน: ผู้ใช้ทั่วไปส่ง subscription ที่มี `https://127.0.0.1:19443/audit` แล้วเรียก `/notifications/test`; listener จำลองได้รับการเชื่อมต่อจาก backend จริง 1 ครั้ง แม้การส่ง push จะจบด้วย `failed: 1` เพราะ listener ปิด socket

ผลกระทบ: เกิด server-side request forgery/การเข้าถึงเครือข่ายจากฝั่ง server เมื่อเปิด VAPID ใช้งาน การทดลองพิสูจน์การเชื่อมต่อ loopback เท่านั้น ยังไม่พิสูจน์การอ่านข้อมูลภายในหรือข้าม TLS validation

แนวแก้: อนุญาตเฉพาะ origin ของ push providers ที่รองรับ ตรวจ HTTPS/port และป้องกัน loopback/private/link-local รวมผล DNS ที่ใช้เชื่อมต่อจริง จำกัดจำนวน subscriptions และเวลาเชื่อมต่อด้วย

### A03 — P1: ปลอม forwarded IP เพื่อเลี่ยง rate limit เมื่อเข้าถึง backend ตรง

ตำแหน่ง: [configure-app.ts:8](<D:/Web App Project/expense-tracker/backend/src/config/configure-app.ts:8>) และ `docker-compose.yml` พอร์ต backend 3001

ค่าเริ่มต้น `trust proxy = 1` เชื่อ header จาก caller ที่เข้าถึง backend โดยตรง ขณะที่ Compose เปิดพอร์ต 3001 บนทุก interface

หลักฐาน: เรียก forgot-password ด้วยอีเมล fixture ที่ไม่มีอยู่ 4 ครั้ง ด้วย `X-Forwarded-For` ค่าเดิม ได้ `201,201,201,429`; เปลี่ยนค่า header แล้วคำขอถัดไปได้ 201 ทันที โดยไม่ได้เปลี่ยนเครื่องต้นทาง

ผลกระทบ: เพดานการลอง login/reset/register ถูกเลี่ยงได้ใน topology ที่เปิดทางตรงเข้า backend ไม่ได้หมายความว่า deployment หลัง proxy ที่กรอง header ถูกต้องทุกแบบมีช่องโหว่นี้

แนวแก้: ปิดเส้นทางสาธารณะเข้า backend, trust เฉพาะ proxy ที่รู้จัก และให้ proxy เขียน header ใหม่ ใช้ `TRUST_PROXY_HOPS=0` ในการเรียกตรง พร้อมเพิ่มข้อจำกัดตามบัญชีใน auth routes ที่เหมาะสม ข้อจำกัดของการ trust แบบจำนวน hops สอดคล้องกับ [เอกสาร Express](https://expressjs.com/en/guide/behind-proxies/)

### A05 — P1: Queue ลบรายการที่ยังส่งไม่สำเร็จเพราะ server ล่มชั่วคราว

ตำแหน่ง: [offlineQueue.ts:134](<D:/Web App Project/expense-tracker/frontend/src/utils/offlineQueue.ts:134>)

ทุก error ที่มี `response` ถูกนับเป็นการปฏิเสธถาวร และเมื่อครบ 5 ครั้งจะลบออกจาก IndexedDB รวมถึง 429/500/502/503 ที่อาจหายได้เมื่อระบบกลับมาปกติ

หลักฐาน: enqueue รายการ 99 บาท แล้วให้ sender ตอบ 503 จำลอง 5 รอบผ่าน queue จริงใน browser → `dropped: 1`, รายการคงเหลือ 0 ไม่มีข้อมูลบน server ให้กู้จาก History

แนวแก้: เก็บรายการจนส่งสำเร็จหรือผู้ใช้ยืนยันลบ แยก retryable errors ออกจากข้อมูลไม่ถูกต้อง ใช้ backoff สำหรับ 429/5xx และให้รายการที่ต้องแก้ไขมีหน้าดู/แก้/ส่งใหม่ได้

### A10 — P2: reset token เดียวเปลี่ยนรหัสผ่านสำเร็จพร้อมกันสองครั้ง

หลักฐาน: สร้าง reset token fixture ที่ยังไม่หมดอายุ แล้ว POST reset-password พร้อมกันสองคำขอด้วยรหัสผ่านต่างกัน ได้ HTTP `201,201` ทั้งคู่

ผลกระทบ: token ไม่ได้ใช้ครั้งเดียวตามที่คาด รหัสผ่านสุดท้ายขึ้นกับลำดับเขียน; ผู้ที่มี reset link อยู่แล้วสามารถแข่งกับเจ้าของได้ ไม่ได้เป็นช่องทางเดา reset token

แนวแก้: ใช้ transaction พร้อม lock หรือ conditional UPDATE ที่ตรวจ hash+expiry แล้ว consume token ในคำสั่งเดียว ตรวจ affected rows = 1 และเพิ่ม tokenVersion แบบ atomic

### A11 — P2: PATCH amount=null หลุด validation จนตอบ 500

ตำแหน่ง: [expense.dto.ts:62](<D:/Web App Project/expense-tracker/backend/src/modules/expenses/dto/expense.dto.ts:62>) และ [expenses.service.ts:247](<D:/Web App Project/expense-tracker/backend/src/modules/expenses/expenses.service.ts:247>)

`@IsOptional()` ข้าม null แต่ service นำ null ไปใส่ entity ด้วย `Object.assign` แม้การคำนวณผลต่างจะใช้ amount เก่าผ่าน `??`

หลักฐาน: รายการ 25 บาท PATCH `{ "amount": null }` → HTTP 500 จาก database constraint; อ่านกลับยังเป็น 25 บาท ยืนยันว่า transaction rollback และยังไม่พบยอดเสียหายในกรณีนี้

แนวแก้: แยก omitted กับ null สำหรับ fields ที่ห้ามว่าง ให้ validation ตอบ 400 ก่อนถึง database; อนุญาต null เฉพาะ field ที่มีความหมายเป็นการล้างข้อมูลจริง
